# ZOS AI OS 产品原则（长期）

> 本文件是 ZOS AI OS 的**长期产品宪法**，适用于所有版本（v1.x 及以后）。当具体实现与原则冲突时，以原则为准。
> 状态：v1.2.1 Production Observation 已冻结；本文件独立于版本迭代，只随认知升级而演进。

---

## 一、ZOS 定位

**ZOS 是企业 AI 经营操作系统，不是普通工具。**

- **操作系统，而非工具**：ZOS 沉淀企业经营数据、编排多个业务 Agent、提供统一的经营驾驶舱与决策辅助；普通工具只是单点功能脚本。
- **判断标准**：一件事是否属于 ZOS 的范畴，看它是否服务于「经营决策闭环」——能否让企业的经营数据被持续看见、被分析、被辅助决策。一次性、无沉淀的任务不纳入核心。
- **角色**：ZOS 是经营者的「副驾驶」，不是「替驾驶」。它增强人的判断，不取代人的责任。

---

## 二、价值闭环

```
真实经营
   ↓
ZOS 辅助
   ↓
SUCCESS / ISSUE
   ↓
Production Review
   ↓
版本规划
   ↓
系统进化
```

- **真实经营**：所有价值的起点。ZOS 必须在真实业务流中被人使用，而非演示。
- **ZOS 辅助**：在经营过程中提供数据聚合、风险洞察、AI 日报、待办审核等能力。
- **SUCCESS / ISSUE**：同一过程的双面——既记录 ZOS 真正帮到业务的成功案例（价值证据），也暴露不足与缺陷（改进输入）。
- **Production Review**：在固定窗口（如 7 天观察期）对 SUCCESS 与 ISSUE 做结构化复盘，输出唯一开发依据。
- **版本规划**：复盘结果落入 A 必须 / B 优化 / C 暂缓 需求池，形成下一版本的范围。
- **系统进化**：新版本上线，回到真实经营，闭环继续。

> 闭环不靠一次性发布完成，而靠「观察 → 复盘 → 规划 → 进化」的持续迭代。

---

## 三、Agent 原则

> 约束对象：ZOS 内所有 AI Agent（风险中心、经营日报、项目管家等）。

1. **AI 负责分析和建议**
   - Agent 产出洞察、结论、推荐动作；不代替业务方完成终局判断。
2. **不直接替代最终决策**
   - 关键经营结论（如风险定级、资源调度）须由人确认；AI 给出依据，人拍板。
3. **不绕过审批**
   - 任何需要他人知会或批准的动作，必须经过既有审批/审核流（如 Inbox 待审核），不得静默代执行。
4. **不直接修改核心事实源**
   - Agent 只对索引/缓存/草稿做读写；绝不直接写入业务事实源（飞书多维表、Supabase 业务表等生产数据）。只读接入，写回需明确授权与审批。

---

## 四、数据原则

> 约束对象：ZOS 对所有业务数据的接入、缓存与呈现。

1. **事实数据只读**
   - 生产事实源（飞书、业务数据库）一律只读接入；ZOS 不持有写入生产事实源的能力。
2. **修改需要审批**
   - 任何对业务数据的变更诉求，须走审批/审核流程，由责任人确认，不自动生效。
3. **保留数据来源**
   - 每条展示数据须可追溯其来源系统、来源表、同步时间；不凭空生成、不臆造指标。
4. **保持可追溯**
   - 数据链路、AI 结论、版本变更均可审计；出问题能定位到「何时、从哪、由谁/何 Agent 产生」。

---

## 五、版本原则

**任何 V 版本升级，必须依次经过以下六个阶段，缺一不可：**

```
开发 → 测试 → Release → 部署 → 观察 → Review
```

| 阶段 | 要求 |
|------|------|
| 开发 | 明确范围与原则对齐；不引入超出本期目标的能力 |
| 测试 | 含回归、数据真实性、PWA 等；全部通过方可晋级 |
| Release | 生成发布文档与部署清单，固化版本号与日期 |
| 部署 | 经授权环境部署；不修改业务逻辑、不触碰密钥 |
| 观察 | 冻结开发，采集真实使用数据、SUCCESS、ISSUE |
| Review | 输出版本复盘，作为下一版本唯一开发依据 |

> 例：v1.2.1 已走完 开发→测试→Release→部署，当前处于 **观察** 阶段，待 7 天 Review 后进入 v1.3 规划。
> 观察期禁止提前开发下一版本；Review 未产出前，不启动新 V 版本。
