# ZOS CEO OS v1.3 全阶段升级设计规格

**日期**：2026-08-02  
**状态**：已由朱帅于 2026-08-02 确认按规格执行
**目标版本**：v1.3.0  
**生产载体**：GitHub Pages PWA + Supabase + 飞书开放平台

## 1. 目标

将当前深色 CEO 指挥中心从“只读汇总页面”升级为朱帅可日常使用的经营决策操作系统，覆盖以下八项明确能力：

1. 待我决策中心；
2. 数据健康中心；
3. 万嘉、花火经营目标与差距；
4. 每日 CEO 简报；
5. Mac、Windows、iPhone、Android 四端行动同步；
6. 飞书受控审核与回写；
7. 手机端行动优先重排；
8. 前端模块化、审计与运行监控。

本版本必须延续现有事实边界：飞书 ERP、合同及当前项目源是业务实时事实；Obsidian 只提供知识元数据；AI 只生成建议、草稿或更新提案，不得把推断写成事实。

## 2. 当前基线

现有 v1.2.3 已具备：

- 深色 CEO 指挥中心与 375px / 768px / 1280px 响应式布局；
- Supabase 邮箱密码、邮件链接登录及单用户 RLS；
- `tasks`、`inbox`、`projects`、`commands` 四类本地记录的跨端同步基础；
- 万嘉、花火、企业项目及 Obsidian 元数据的只读缓存；
- 风险探测器、项目经理日报草稿和人工审核出口；
- 飞书字段漂移诊断、只读请求和安全错误分类。

当前缺口：

- `index.html` 约 4,635 行，页面、状态和业务逻辑耦合；
- 没有持久化经营目标、目标差距和历史趋势；
- 没有统一的待决策队列及决策状态；
- 没有来源巡检历史、记录数、耗时和新鲜度；
- 四端同步仍依赖手动触发，缺少冲突可视化；
- 飞书只有读取能力，没有安全的预览、确认、执行、回读和审计链；
- 日报需手动生成，手机首页信息密度仍偏桌面化；
- 生产错误缺少脱敏运行事件与可核验健康视图。

## 3. 方案比较与选型

### 方案 A：受控闭环增量升级（采用）

保留 GitHub Pages PWA、Supabase 登录与现有只读数据通道；将前端逐步模块化，新增目标、健康、审批和审计数据结构。飞书更新采用“预览 → 单次确认 → 白名单执行 → 回读验证”的服务端闭环。

优点：延续现有数据与链接，迁移风险可控，能满足全部阶段目标。  
代价：需要数据库迁移、两个受保护的 Edge Function 和较完整的回归测试。

### 方案 B：重建为服务端经营平台（不采用）

改用完整前端框架和服务端任务引擎，所有页面及数据重新实现。

优点：长期架构最整洁。  
缺点：会扩大迁移、登录、PWA、缓存和飞书兼容风险，不适合作为本轮连续升级。

### 方案 C：仅扩充前端展示（不采用）

继续在单文件里增加卡片，飞书审批只做导出模板。

优点：发布快。  
缺点：无法完成真实四端同步、审计、数据健康和安全回写，不满足目标。

## 5. 核心业务模块

### 5.1 待我决策中心

#### 输入

- 风险探测器产生的高风险及延期项；
- 万嘉待收款、待跟进与异常动销项；
- 花火待交付、待回款、利润亏损或档期异常项；
- 企业项目中的高风险、超期和负责人缺失项；
- AI 日报及知识草稿的待审核项；
- 飞书更新提案。

#### 决策项结构

```text
id
source
sourceRecordId
company
category
severity
title
factSummary
recommendedAction
owner
dueAt
impact
sourceUpdatedAt
status: open | approved | rejected | deferred | resolved
resolutionNote
createdAt / updatedAt / revision / deviceId
```

#### 规则

- `factSummary` 只能来自已经验证的只读数据，不得由 AI 补写事实；
- AI 只能生成 `recommendedAction`，页面必须明确标注“建议”；
- 相同 `source + sourceRecordId + category` 只保留一个活跃决策项；
- 风险消失后自动变为“待确认已解决”，不能静默删除；
- 批准飞书更新只会创建审批记录，不会在浏览器直接请求飞书。

### 5.2 经营目标与差距

#### 目标来源

- 朱帅手工确认的月度或周度目标；
- 经确认后导入的飞书目标字段；
- 不允许根据历史数据自动推断目标。

#### v1.3 指标白名单

万嘉：

- 支付 GMV
- 核销 GMV
- 动销商家数
- 视频投稿数
- 直播场次
- 预估佣金

花火：

- 合同金额
- 已回款
- 待回款
- 在制项目数
- 待交付项目数
- 亏损风险项目数

每项展示：目标、实际、差值、完成率、数据日期、事实来源和状态。缺少目标时显示“目标待设置”；缺少实际值时显示 `—`，不得显示伪造的 0。

#### 历史趋势

每次授权刷新成功后，仅保存指标级聚合快照，不保存飞书正文、合同正文或客户敏感内容。相同用户、来源、指标和日期幂等覆盖。

### 5.3 数据健康中心

为 `wanjia`、`huahuo`、`projects`、`brain`、`sync`、`feishu_write` 展示：

- 当前状态：正常、陈旧、待配置、读取失败、权限不足；
- 最近成功时间；
- 最近尝试时间；
- 记录数；
- 请求耗时；
- 数据契约版本；
- 新鲜度；
- 安全错误码；
- 建议处理动作。

健康中心不显示 App Secret、访问令牌、原始飞书错误体或业务正文。

### 5.4 每日 CEO 简报

#### 生成时机

- 每天首次在已登录状态打开首页时，基于当日数据自动生成一份草稿；
- 同一天、同一数据版本只生成一次；
- 用户仍可手动重新生成，并保留版本号。

#### 固定结构

1. 昨日完成
2. 今日三件事
3. 经营目标差距
4. 高风险与异常
5. 待我决策
6. 待回款与待交付
7. AI 建议动作
8. 数据新鲜度声明

日报写入现有 `inbox` 同步记录，类型为 `daily_brief`，状态默认为待人工审核。未经确认不得发送飞书、写入知识库或转为正式任务。

### 5.5 四端行动同步

#### 同步范围

- 任务
- 收集箱
- 本地项目
- AI 指令
- 决策处理状态
- 经营目标
- 日报草稿

#### 触发时机

- 用户登录成功；
- 应用恢复到前台；
- 网络从离线恢复；
- 本地记录发生变更后的防抖同步；
- 用户点击“立即同步”。

#### 冲突策略

- 非关键文本记录默认使用现有 `updatedAt + revision + deviceId` 确定赢家；
- 目标、决策结果和飞书审批属于关键记录，同一记录在不同设备同时修改时进入“同步冲突”队列；
- 冲突页面并排显示本机版本、云端版本、修改设备和时间，由用户选择保留或合并；
- 删除继续使用 tombstone，任何旧设备不得复活已删除记录。

页面必须显示离线、同步中、已同步、冲突和失败状态，以及最近同步设备和时间。

### 5.6 飞书受控审核与回写

#### 安全原则

- 浏览器永远不保存飞书 App Secret 或 tenant token；
- 飞书 App ID/Secret 仅存在 Supabase Edge Function Secrets；
- 浏览器不能提交任意 app token、table ID、字段名或任意 JSON patch；
- 所有目标表、动作和字段由服务端白名单决定；
- 每条变更必须逐条预览、逐条确认，默认不提供“全部批准”；
- 执行前必须检查源记录未发生变化；
- 执行后必须重新读取并核对实际值；
- 失败不得部分伪装为成功。

#### 两阶段接口

`zos-feishu-approval-preview`：

1. 验证 Supabase 用户 JWT；
2. 校验动作类型和来源记录；
3. 查询飞书当前字段；
4. 返回修改前、修改后、字段差异、快照哈希和十分钟有效的审批 ID；
5. 写入 `previewed` 审计事件。

`zos-feishu-approval-execute`：

1. 验证用户 JWT、审批 ID 和审批状态；
2. 重新读取飞书源记录并核对快照哈希；
3. 如源记录已变化，返回 `source_changed`，要求重新预览；
4. 只更新白名单字段；
5. 回读并逐字段核对；
6. 记录成功或失败审计结果。

#### 初始白名单

首发只允许在服务端确认字段确实存在时启用：

- 负责人
- 状态或阶段
- 下一步动作
- 截止时间
- 审核状态

某张表缺少对应字段时，该动作在 UI 中显示“不可用”，不能动态改写其他相似字段。具体表字段映射由部署环境配置并在数据健康中心回读，不写死在浏览器。

## 6. 数据架构

### 6.1 继续复用

- `zos_records`：本地行动数据的单用户跨端同步；
- `zos_business_cache`：万嘉、花火、项目和企业大脑只读缓存；
- Supabase Auth：邮箱密码及邮件链接登录；
- 现有 Feishu 只读 Edge Function。

### 6.2 数据库迁移

新增一份幂等迁移，包含：

1. 扩展 `zos_records.entity_type`：增加 `decisions`、`targets`；
2. `zos_business_snapshots`：保存日期级聚合指标；
3. `zos_source_health`：保存每个用户、来源的最近健康结果；
4. `zos_feishu_approvals`：保存审批提案、快照哈希、状态和回读结果；
5. `zos_audit_events`：保存脱敏审计事件。

所有表必须：

- 强制 `user_id = auth.uid()` 的 RLS；
- 默认拒绝匿名访问；
- 使用唯一键保证刷新、审批和快照幂等；
- 不保存密码、令牌、Secret、飞书原始响应、合同正文或 Obsidian 正文。

### 6.3 运行事件

审计事件只包含：事件类型、来源、结果、安全错误码、耗时、记录数、关联审批 ID、时间和客户端版本。页面异常文本先归一化后再记录，最多保留 90 天。


拆分原则：

- `index.html` 只保留语义化页面骨架与加载入口；
- 数据模型、业务规则和网络访问不写在视图模块中；
- 视图只能调用明确的 controller 接口；
- 现有 DOM ID、公开函数和 localStorage key 在迁移期间保留兼容层；
- 每完成一个模块拆分即运行全量回归，禁止一次性重写整份页面。

## 8. 数据流

### 8.1 只读经营数据

```text
飞书事实表
  → Supabase Edge Function 读取与字段校验
  → 只读汇总/元数据 + 健康信息
  → PWA 缓存
  → 经营卡片 / 风险 / 目标差距 / 决策候选 / 日报草稿
```

### 8.2 飞书更新

```text
决策项
  → 生成更新提案
  → 服务端预览当前值与目标值
  → 朱帅逐条确认
  → 服务端检查源记录未变化
  → 白名单字段更新
  → 飞书回读验证
  → 审计记录 + 页面结果
```

### 8.3 四端同步

```text
设备本地变更
  → 标准化 revision/deviceId/tombstone
  → Supabase owner-scoped records
  → 其他设备前台恢复或联网时拉取
  → 自动合并或进入关键记录冲突队列
```

## 9. 状态与错误处理

统一使用：

- `synced`：已同步且未过新鲜度阈值；
- `stale`：有缓存但已过阈值；
- `pending`：已登录，等待同步或刷新；
- `confirm`：目标、字段或权限需要确认；
- `conflict`：关键记录存在跨端冲突；
- `failed`：最近操作失败。

业务数据失败时保留上次成功缓存，但必须标注缓存时间和“可能已过期”。审批失败时不得更新本地事实状态；只有飞书回读成功后才能显示“已执行”。

## 10. 隐私与安全

- 飞书、Supabase 凭证不进入 Git、前端、localStorage、日志、审计表或文档；
- Obsidian 仍只上传 path、title、tags、mtime、folder、reviewStatus 等元数据；
- 不读取或上传 Markdown 正文；
- 浏览器只使用 Supabase publishable key 和当前用户会话；
- 所有 Edge Function 请求验证用户身份、请求类型、载荷大小、来源及白名单；
- 增加 Content Security Policy、Referrer Policy 和安全响应头；
- 运行监控只记录脱敏状态，不记录客户、订单、金额明细和正文。
